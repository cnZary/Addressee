# Interoperability validation

## Method

Each supported algorithm must be validated per operation and per key version. Local round trips are recorded separately from independent-implementation results. GnuPG tests use an isolated temporary `GNUPGHOME` and disposable keys; they never read or modify the user's normal GnuPG keyring or Git-signing configuration. The isolated agent configuration disables `scdaemon` so software-key tests cannot access a physical card. Verification time is sampled after receiving each peer-generated signature or message, rather than before running the peer operation.

The test matrix covers, where applicable:

- Generation, public/private import, public export, and policy-controlled private export.
- Detached, attached, and cleartext signatures and verification.
- Encryption, decryption, multiple recipients, and binary/armored messages.
- Sign-then-encrypt and decrypt-then-verify.
- RSA-2048, RSA-3072, RSA-4096, modern and legacy Curve25519, NIST P-256/P-384/P-521, and Ed448/X448.
- v4 and v6 encodings where allowed by the selected compatibility policy.
- Tampered messages, invalid signatures, unknown signers, revocation, expiration, and Key Flags.

Brainpool operations remain unavailable unless cryptographic implementation and independent interoperability tests pass. Historical algorithms are limited by security policy rather than enabled solely because a parser recognizes them.

## Legacy algorithm policy evidence

On 2026-10-29, real rPGP-generated RSA signatures exercised MD5 and SHA-1 in detached, attached, cleartext, and sign-then-encrypt messages. The tests independently checked the underlying signatures before evaluating application policy. MD5 was cryptographically valid but rejected without releasing attached, cleartext, or decrypted plaintext; SHA-1 remained valid with a structured weak-hash warning. Custom SHA-1 rejection was also exercised. Modern v4 and v6 messages produced no legacy warning. Results are in `build/legacy-policy-core-20261029.log`.

Real SEIPDv1 messages using IDEA, TripleDES, CAST5, and Blowfish verified the default allow-with-warning behavior and per-algorithm rejection. Rejected ciphers did not write plaintext staging. A real FFI MD5/SHA-1 signed-and-encrypted message test verified memory output, stable algorithm identifiers, and file-staging cleanup: MD5 produced no plaintext or destination file, while SHA-1 produced the expected content with its warning. Results are in `build/legacy-policy-ffi-files-20261029.log`.

These are local policy and format tests, not claims of independent GnuPG support for weak algorithms. The independent suite continues to use modern algorithms for new signatures and encryption; its current results remain separate below.

## Capability policy evidence

On 2026-10-30, component-level registry tests covered Sign, Verify, Encrypt, and Decrypt across detached, attached, cleartext, encrypt-only, and sign-then-encrypt workflows. Disabled operations returned policy errors without output; disabled verification was not evaluated cryptographically and blocked in-memory plaintext release and file-staging commit, while unsigned encrypted messages remained usable. Missing registry entries and unknown remote backends failed closed. Card-provider simulations checked that runtime discovery is mandatory before resolution, that public-key encryption remains local, and that an authenticated P-256 binding can proceed without relaxing the recorded hardware-evidence requirements. These simulations are not new physical-card evidence.

An independent GnuPG 2.5.24 case generated an unprotected disposable RSA certification primary with real DSA signing and ElGamal encryption subkeys in an isolated `GNUPGHOME`. The application imported and reprotected the private certificate, rejected DSA signing before producing an artifact, rejected the GnuPG DSA detached signature without cryptographic evaluation, rejected ElGamal encryption without output, and rejected the GnuPG ElGamal-encrypted message before private-key decryption. This validates fail-closed policy enforcement for real imported historical algorithms; it does not enable or claim end-to-end DSA or ElGamal support.
