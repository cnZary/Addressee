## Apple API evidence

The current iPhoneOS SDK contains `NFCISO7816Tag` and `NFCISO7816APDU`, available from iOS 13. Apple's [ISO 7816 AID declaration documentation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.developer.nfc.readersession.iso7816.select-identifiers) also lists iOS 13. The application declares the standard OpenPGP application prefix `D27600012401`, rather than a vendor-specific identifier. NFC behavior remains unverified on a physical iPhone.

Security framework documentation in the SDK states that the Secure Enclave token supports only 256-bit elliptic-curve keys, generated in the Secure Enclave, and cannot import pregenerated keys. CryptoKit exposes P-256 Signing and Key Agreement APIs. These types and raw ECDH `SecKeyAlgorithm` passed an iOS 16 compile probe. That compile probe is not hardware evidence; the physical results below are limited to the listed P-256 operations.

Apple's [`TKSmartCardSlotManager` documentation](https://developer.apple.com/documentation/cryptotokenkit/tksmartcardslotmanager) lists iOS 9 and requires `com.apple.security.smartcard`. However, the current [entitlement documentation](https://developer.apple.com/documentation/bundleresources/entitlements/com.apple.security.smartcard) lists only macOS 10.10 in its platform metadata. This documentation discrepancy must not be resolved by assumption. iOS entitlement provisioning, system CCID driver access, USB-C device discovery, and actual APDU exchange remain unverified. macOS PC/SC access is not evidence of iOS USB-C support.

On 2026-10-25, `bash scripts/test-apple-platform-apis.sh` compiled and linked the complete `AppleSmartCardTransport` module for `arm64-apple-ios16.0`. `otool` confirmed linkage to CryptoTokenKit and Core NFC. The script also validates the smartcard and NFC entitlements and the OpenPGP AID declaration, and runs as part of `test-ios.sh`. These are build and declaration checks only; no iPhone was available to execute them and no physical USB-C compatibility is claimed. The SDK emitted a non-fatal Clang sysroot-target warning during the direct `swiftc` link, which is retained in `build/apple-platform-api-tests.log`.

CryptoTokenKit also exposes `createNFCSlot` and `isNFCSupported`, but Apple's documentation introduces those APIs in iOS 26. They are a separate newer API path and are not used to claim iOS 16 support or to replace the Core NFC transport.

## CanoKey protocol expectations

CanoKey's public OpenPGP protocol documentation describes OpenPGP Card 3.4 behavior, short APDUs, `61xx` response continuation, and firmware-3.1.0 command chaining for selected instructions. The documentation currently lists cardholder-certificate writing, key import, and PSO Decipher as chaining-capable commands. Each command must still be gated by discovered capabilities and safe tests.

The firmware version supplied for the authorized test device is 3.1.0, but firmware must not be used as the sole device identity. Extended Length APDU is considered unsupported until actual capability data and safe transport tests establish otherwise.

## Native card association and management implementation

The application persists a card-to-public-certificate association, not a transport, reader, live session, or PIN. Association starts from the corresponding public certificate in **Keys**; **More > Hardware Key Management** only lists linked devices and manages their contents. Each certificate can have its own card association, with an independent stored binding and connection preference. Legacy transport fields are ignored during restoration and omitted on the next write. Last-used connection preferences are separate UI defaults. Each private-key or management operation selects NFC or USB, with identity revalidation and no fallback device. In the default single-hardware-key mode, each USB operation takes one current reader snapshot and uses the reader only when exactly one is available. No or multiple readers produce an explicit error instead of a stale-preference or enumeration-order fallback. Enabling **More > Application Settings > Multiple Hardware Keys** displays the reader picker and requires an explicit current selection; this setting does not limit the number of certificate/card associations. Reader lists are not periodically polled. Restoring an association does not open hardware or attach a private-key provider. Explicit unlinking removes the association; a disconnected session does not.

NFC private-key operations collect a one-shot PIN before opening the system reader, then use one session for binding and PIN-policy validation, provider attachment, the private-key operation, detachment, and closure. Cancelling PIN entry does not open NFC. The prompt uses conservative 6–64-byte limits without inventing retry counts; the actual card policy is still checked in Rust before `VERIFY`. Physical touch occurs in that session under conservative touch-if-requested system-alert guidance, not through an app acknowledgement. USB operations keep one short session with native PIN/touch callbacks. The opted-in device-test observer expects one session per NFC private-key operation.

The SDK's `NFCReaderSession.alertMessage` documentation explicitly permits dynamic updates in any thread context while the session is valid. The transport sets the initial message before `begin()`, then updates it on its confined queue for card-detection/validation, private-key or management execution, and successful closure. Application session tests record these forwarded messages and capture the message present when an operation starts. They do not establish that the system sheet rendered them on a physical iPhone.

CryptoTokenKit uses the public raw `transmit(_:reply:)` API to preserve exact APDU commands and complete responses, including status bytes. The previous high-level `send` helper could perform implicit APDU length handling; it is no longer used. Host-only tests verify raw-response preservation and rejection of missing or short responses. Diagnostic presentation retains the underlying error and includes only a stage, transport, allowlisted system error code, and raw status word when available. Cleanup errors do not replace the original private-key error. No physical USB interoperability is established by these implementation and host checks.

A linked device's management page selects a connection for each operation, verifies the associated certificate components and card identity, and never attaches its private-key provider. It supports explicit public-card inspection, User/Admin PIN changes, and reversible Off/On touch-policy changes followed by fresh inspection. PINs are not persisted. Fixed, Cached Fixed, and unknown touch policies cannot be changed through this interface. Retry counters below two stop PIN verification or writing, and an incorrect PIN is not retried automatically. Card key generation, import, algorithm reconfiguration, and factory reset remain unimplemented in the application.

The eleven management protocol tests use synthetic cards and PINs and do not access hardware. They cover public-only reads, identity changes, exact raw-PIN commands, optional absent KDF data, KDF read failures, retry safeguards, one failed PIN attempt, restricted touch writes, and malformed Key Information. The vendored card parser rejects short or odd-length Key Information before indexing it; card ECDH attributes are not confused with certificate ECDH KDF parameters. The vendored card crate passed 44 unit tests and one doctest with the local changes. No physical card PIN or touch policy was changed for these tests. Native iOS association, automatic NFC dismissal, private-operation reconnection, and management writes remain physically unverified.

## Test gates

Read-only inspection and destructive tests must be separate executables. Credentials must come from hidden interactive input and must never appear in source, process arguments, repository files, or logs. Destructive operations require exact reader, USB, AID, and runtime-authorization matching. The YubiKey exclusion has no fallback or override.
